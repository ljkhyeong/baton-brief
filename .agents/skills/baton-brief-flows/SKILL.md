# BATON BRIEF 공통 흐름

## 맥락을 확립한다

- `AGENTS.md`, `HANDOFF.md`, `README.md`, 영향받는 PRD와 관련 ADR을 읽는다.
- ADR-0002의 다섯 모듈과 PRD-0002부터 PRD-0014까지를 현재 작업 범위로 사용한다. 실제
  구현 상태와 검증 근거는 `HANDOFF.md`에서 확인하고, 외부 연동·실제 네트워크 실행·운영
  배포로 확대하지 않는다.
- 이 보완 절차를 사용하기 전에 기존 규칙을 검색하고 가장 좁게 일치하는 BRIEF 스킬을
  선택한다.

## 서비스 소유권을 보존한다

- BATON이 원본 도메인 사실, 멤버십, 권한 부여와 연속성 판정을 소유하게 한다.
- WATCH가 URL 점검과 상태 사실을, RELAY가 구독과 제공자 전달을, GO가 공개
  링크 수명주기를 소유하게 한다.
- BRIEF는 자체 멱등 수신함, `AttentionItem` 투영, 로컬 `sourceCursor`,
  작업공간/시즌별 `generation`, 재구축 근거와 불변 `BriefEdition`만 소유한다.
- 커밋된 원본 이벤트를 소비한다. BRIEF 가용성을 BATON 원본 트랜잭션과
  결합하지 않는다.
- 다른 서비스의 엔티티, 마이그레이션, 자격 증명 또는 데이터베이스를 공유하지 않는다.

## 채택한 사실에 따라 변경한다

1. 요청을 소유하는 서비스, PRD 동작과 장기 ADR 결정에 연결한다.
2. ADR-0002를 정확히 적용한다. Kotlin/JVM 2.3.21, Java 21 도구 체인과 JVM 21 바이트코드 대상,
   JDK 21 실행 환경, Spring Boot/BOM 4.1.0, Kotlin DSL을 사용하는 Gradle wrapper 9.2.1,
   PostgreSQL 18.4, Spring JDBC `JdbcClient`와 Flyway를 사용하고 JPA는 사용하지 않는다.
   Java 25 호환성은 검증했지만 기능 필요성과 고정된 CI/실행 이미지 기준이 생길 때까지
   보류한다.
3. `domain`, `application`, `adapter-in-web`, `adapter-out-persistence`, `bootstrap` 다섯
   모듈을 유지한다. 의존은 `bootstrap`/어댑터에서 `application`, 다시 `domain`으로
   향하게 한다. 어댑터끼리 의존하지 않고 내부 모듈은 외부 모듈에 의존하지 않는다.
4. PRD-0002부터 PRD-0014까지 채택한 인증 없는 내부 로컬 MVP 계약을 따른다. 현재 구현
   범위는 `HANDOFF.md`에서 확인한다. 후속 결정이 채택하기 전에 JDK 공급자, 실행 컨테이너
   이미지, 브로커, 스케줄러, 생산자 변경, 외부 시스템 어댑터, 운영 배포 또는 운영
   인증·인가 계약을 가정하지 않는다.
5. 로컬 PostgreSQL 18.4 의존 서비스에는 `compose.yml`을 사용한다. Spring Boot의 표준
   데이터 원본 및 Flyway 속성/환경변수를 우선하고 프레임워크 설정에 프로젝트 전용 별칭을
   추가하지 않는다.
6. 이후 장기 기술 스택, 아키텍처, 전송 또는 운영 선택은 ADR에 기록한다.
7. 비즈니스 불변식을 어댑터와 독립적으로 유지하고, 시간 의존 동작에 `Clock`을 주입하며,
   시간대와 구간 의미를 명시한다.
8. 실제로 구현하거나 채택한 동작과 결정에 대해서만 관리 문서를 갱신한다.
9. 새 문서와 수정 문서의 제목·본문·상태·설명은 한글을 기본으로 작성한다. 코드 식별자,
   API 경로, HTTP 표기, 파일명, 명령어와 공식 기술명은 원문을 유지한다.

## 단순한 구현을 우선한다

- 같은 동작과 호출 지점을 `rg`로 찾고 같은 이유의 중복을 함께 정리한다.
- 직접 구현하기 전에 Kotlin 표준 API와 관용 표현을 먼저 확인한다. Kotlin에 대응 기능이
  없으면 Java 21 JDK API를 사용하고, 이어서 Spring Boot, `JdbcClient`, Jackson과 현재
  의존성의 표준 API·자동 구성·설정 속성을 확인한다. 더 앞선 선택지가 현재 계약과 실패
  시점을 보존하면 직접 구현하거나 아래 단계의 API로 우회하지 않는다.
- 입력 형태는 웹 DTO, 도메인 불변식은 도메인, 저장 무결성은 PostgreSQL에서 소유한다.
  같은 소유자가 같은 실패 시점에 반복하는 검증만 제거하고, 서로 다른 신뢰 경계의 방어는
  유지한다.
- 생성과 주간 범위 최신 조회의 `weekStart`·`zoneId` HTTP 표현 규칙은 같은 웹 DTO 검증을
  재사용한다. 주간 조회는 기존 저장 스냅샷을 읽으며 별도 검증 도우미, 스키마·마이그레이션
  또는 현재 투영 재조합을 추가하지 않는다.
- 에디션 리비전 근거는 기존 `AttentionItem`의 `lastRevision`·`revisionGap`을 새 항목에
  직접 고정한다. 별도 근거 조회 모델이나 변환 래퍼를 만들지 않고, V3 이전 행의 알 수
  없는 값은 두 필드 모두 `null`, 신규 저장은 두 필드 모두 필수로 구분한다. 근거는 응답,
  `stateFingerprint`와 기존 항목 동등성 기반 비교에 일관되게 포함한다.
- 불변 에디션 전체 응답에는 선택된 에디션의 불투명 `ETag`를 사용한다. Kotlin이나 직접
  분기로 `If-None-Match`를 파싱하지 않고 Spring MVC가 `ResponseEntity` 헤더로 수행하는
  표준 조건부 요청 처리를 사용한다. 별도 본문 해시, 캐시 저장소와 TTL을 만들지 않는다.
- 이상 수신 증거 이력은 기존 안전한 수신 증거 표현과 `ingestionSequence` 키셋을
  재사용한다. `limit + 1` 조회로 다음 커서를 판단하고 별도 전체 개수, 범용 필터 도우미,
  테이블·마이그레이션과 인덱스를 계약 없이 추가하지 않는다.
- 현재 관심 항목 단건 조회는 이벤트 적용이 사용하는 복합 기본 키 조회와 기존 응답
  표현을 재사용한다. 별도 조회 모델, 마이그레이션과 인덱스를 단건 계약에 추가하지 않는다.
- 현재 활성 관심 항목 목록은 두 필드를 하나로 묶은 커서, 복합 기본 키 행 값 비교와
  `limit + 1`을 사용한다. 현재 투영의 요청 간 비스냅샷 의미를 문서화하고 offset·전체
  개수·새 인덱스와 에디션 선정 정렬을 추가하지 않는다.
- 한 번 쓰는 식을 이름만 바꾸는 도우미, 단일 변형을 위한 전략·팩터리, 한 필드만 감싸는
  전달용 래퍼를 만들지 않는다. 책임·실패 경계·안정적인 의미 중복이 있을 때만 추출한다.
- 자동 구성 대체는 실제 애플리케이션 컨텍스트에서 확인한 뒤 커스텀 빈을 지운다. 소스 모양이
  비슷하다는 이유만으로 트랜잭션, 잠금, 정규화나 오류 계약을 제거하지 않는다.
- `retain-all` 수신 기록 재생은 `JdbcClient`/JDBC의 표준 스트림과 `use`로 자원을 닫아
  순서대로 처리한다. 전용 페이지네이터, 배치 프레임워크, 잠금 관리자, 백그라운드 작업
  래퍼나 체크포인트 추상화를 채택된 계약 없이 만들지 않는다.
- Spring MVC 요청 오류는 PRD-0004의 표준 Problem Details 자동 구성을 우선한다. 별도 오류
  DTO나 전역 처리기를 만들기 전에 자동 처리 범위와 민감정보 비노출 기본값을 확인한다.
- 최소 상태 확인은 Spring Boot Actuator의 aggregate health와 자동 구성된 DB contributor를
  사용한다. 커스텀 controller, DTO, `HealthIndicator`, 상태 매퍼와 DB 확인 SQL을 만들지
  않는다. Spring Boot 4.1의 health probes 기본값은 `true`이므로 배포 계약을 채택하기
  전에는 `management.endpoint.health.probes.enabled=false`를 유지한다.
- 완료한 변경은 주된 목적에 따라 `설정`, `기능`, `수정`, `리팩터`, `테스트`, `문서`로
  나누고 명시적인 경로만 스테이징해 각각 커밋한다.

## 검증 결과를 사실대로 기록한다

- 저장소에서 확인한 명령만 실행한다. 빌드 또는 테스트 명령을 만들어내지 않는다.
- `./gradlew test`와 `./gradlew :bootstrap:bootJar`를 저장소 전체 기준으로 사용한다.
- 실행 가능한 가장 좁은 검증부터 시작하고 계층 횡단 변경에는 범위를 넓힌다.
- 같은 위험을 여러 계층에서 반복 검증하거나 커버리지 수치를 위해 단순 매핑과 프레임워크
  자체 동작을 테스트하지 않는다. 핵심 계약을 가장 가까운 소유 경계에서 한 번 검증한다.
- 변경하지 않은 계층의 검증을 반복하지 않는다. 계층 횡단 변경의 전체 테스트와 실행 JAR
  생성은 최종 상태에서 한 번 수행한다.
- 계약 변경에는 생산자/소비자 호환성과 재생 동작을 검증한다.
- 투영 또는 에디션 변경에는 중복, 순서가 뒤바뀐 전달, 재구축과 고정 시각 동작을
  검증한다.
- 스캐폴드 근거만으로 외부 연동, 배포, 내구성 또는 종단 간 동작을 주장하지 않는다.
