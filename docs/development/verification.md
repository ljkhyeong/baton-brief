# 변경 범위별 검증

에이전트의 로컬 검증 기준이다. GitHub Actions의 필수 검증은 그대로 따른다.
계약·마이그레이션·배포의 세부 검증은 [작업별 스킬](../../AGENTS.md)을 함께 적용한다.

## 실행 순서

1. 현재 경로·브랜치·작업 중 변경과 [인수인계](../../HANDOFF.md)의 관련 근거를 확인하고
   `git rev-parse HEAD`로 작업 시작 커밋을 기록한다. 중간 커밋 후에도 이 기준을 유지한다.
2. 변경한 동작을 확인할 최소 검증과 전체 검증이 필요한 조건을 정한다. 작은 수정은 한 줄이면 충분하다.
3. 파일 수정 직후 아래 파일 검사를 실행한다. 함께 수정해야 컴파일되는 파일은 한 번에 전달한다.
   실행 중인 검증의 소스를 수정하거나 같은 작업 폴더에서 다른 Gradle 검증을 시작하지 않는다.
4. 실패하면 원인을 수정하고 실패한 테스트부터 실행한다. 통과하면 영향이 남은 범위만 확인한다.
5. 작업 종료 전 전체 diff·구조 검사와 선택한 동작 검증을 마친 뒤 결과를 기록하고 커밋한다.
   통과 뒤에 관행적으로 검증 범위를 넓히지 않는다.

## 파일 검사와 전체 변경 검사

Python 3.11 이상과 Git, 기존 Gradle wrapper를 사용한다. 에이전트는 아래 명령을 파일 수정 직후와
작업 종료 전에 호출한다. 편집기 저장 이벤트를 감시하는 상주 프로세스나 앱 전역 훅은 설치하지 않는다.

```shell
# 수정 직후: 경로는 저장소 루트 기준이며 여러 파일을 한 번에 지정할 수 있다.
python3 scripts/verify-feedback.py files application/src/main/kotlin/com/personal/baton/brief/application/BriefService.kt

# 종료 전: 작업 시작 때 기록한 실제 커밋으로 바꾼다.
python3 scripts/verify-feedback.py final <시작-커밋>
```

| 파일 | 수정 직후 자동 검사 |
| --- | --- |
| Kotlin·Java 제품 코드 | 해당 모듈 `classes`로 컴파일 |
| Kotlin·Java 테스트 | 해당 모듈 `testClasses`로 컴파일 |
| Gradle 설정·버전 catalog | `help`로 빌드 설정 평가 |
| 셸·Python·TOML | `bash -n`·표준 AST·TOML 파서로 문법 확인 |
| 모든 변경 파일 | Git 공백 오류 검사 |

문서 링크·표현, YAML 설정의 실제 유효성, 제품 동작은 이 빠른 검사만으로 보장하지 않는다.
변경 범위 표와 해당 스킬의 검증을 이어서 적용한다.

`final`은 시작 커밋 이후의 현재 파일 diff와 별도의 staged diff, Git에서 무시하지 않은 새 파일을
출력한다. 중간 커밋·삭제·이름 변경도 검사 범위에 넣는다. 출력 전체를 읽고 중복 구현·검증 위치·
서비스 책임·불필요한 확장을 검토한다. 자동 규칙 통과가 이 검토를 대신하지 않는다.
검사는 현재 작업 파일을 대상으로 하므로 커밋할 때 검증한 내용과 같은 파일을 스테이징한다.

코드·빌드 변경이 있으면 `:bootstrap:architectureTest`로 전체 제품 클래스의 아래 규칙을 검사한다.

- 안쪽 계층은 어댑터·구성 루트에 의존하지 않으며 어댑터끼리 참조하지 않는다.
- 웹 어댑터는 저장 포트 `BriefPersistencePort`를 직접 사용하지 않는다.
- 도메인·유스케이스는 프레임워크에 의존하지 않는다.
- SQL·저장 프레임워크는 영속성 어댑터와 구성 루트에서만 사용한다. 입력 검증용 Hibernate Validator는 허용한다.

구조 검사는 Spring·DB를 기동하지 않는다. Gradle `test`와 CI에서도 자동 실행하며 일반 테스트에서는
같은 구조 테스트를 제외해 중복을 막는다. 파일·의존성 변경이 없으면 Gradle의 기존 성공 결과를 재사용한다.
문서만 바꾼 경우에는 Gradle을 실행하지 않는다. 관련 동작 테스트는 아래 기준에 따라 별도로 선택한다.

검사 도구 자체를 바꾸면 `python3 -m unittest discover -s scripts -p 'test_*.py'`로 변경 파일 선택과
실패 전파를 확인한다. 같은 검증을 CI에서도 실행한다.

## 검증 범위 선택

| 변경 | 기본 검증 | 범위를 넓힐 조건 |
| --- | --- | --- |
| 문서·지시·스킬 | 바뀐 링크·형식과 `git diff --check` | 스킬 메타데이터 변경 시 메타데이터 검사, 계약 ZIP에 포함되는 문서·링크 변경 시 `contractsZip` |
| 테스트 이름·fixture·테스트 구조 | 바뀐 테스트 선택 실행 | 공용 fixture의 다른 사용처에 영향이 있으면 해당 테스트도 실행 |
| 한 영역의 실행 동작 | 해당 동작의 단위·통합 테스트 | 다른 계층의 동작·저장·HTTP 계약까지 바뀌면 관련 검증 추가 |
| 여러 계층의 실행 동작·공통 빌드·의존성 | 최종 상태의 `test :bootstrap:bootJar` | 실행 환경도 바뀌면 격리 기동, 계약 팩 입력도 바뀌면 `contractsZip` |
| DB 마이그레이션 | 대표 이전 데이터의 업그레이드와 관련 조회·저장 테스트 | 영향받는 데이터·제품 동작 범위에 따라 확대 |
| Compose·이미지·인증·배포 설정 | 해당 스킬의 설정·실행·인증 검증 | 실제 연결·권한·실행 환경이 바뀐 범위까지 확인 |
| 커밋·fast-forward 병합 | 검증 기준과의 차이 및 작업 트리 확인 | 충돌 해결이나 미검증 코드가 추가되면 해당 동작 검증 |

파일 수나 여러 디렉터리에 걸쳤다는 이유만으로 전체 테스트를 선택하지 않는다.
테스트만 바꾼 작업에 실행 JAR 생성은 기본 검증이 아니다. 사용자가 재검증을 요청하면 그 범위를 따른다.

## BRIEF 명령 예시

한 번의 Gradle 호출에 필요한 태스크를 모은다. 아래 명령을 모두 순서대로 실행하는 것은 아니다.

```shell
# 도메인 동작을 바꾼 경우
./gradlew :domain:test --tests 'com.personal.baton.brief.domain.AttentionProjectorTest'

# 현재 목록의 필터·커서 동작을 바꾼 경우
./gradlew :bootstrap:test --tests 'com.personal.baton.brief.BriefMvpIntegrationTest.현재 관심 항목 목록은 필터와 복합 커서를 지킨다'

# 이벤트 계약과 배포용 계약 팩 입력을 함께 바꾼 경우
./gradlew :bootstrap:test --tests 'com.personal.baton.brief.BriefEventContractTest' contractsZip

# 여러 계층의 실행 동작이나 공통 빌드·의존성을 바꾼 경우
./gradlew test :bootstrap:bootJar
```

선택 실행 결과는 해당 테스트 범위의 근거다. `NO-SOURCE`나 선택된 테스트 0건은 검증 성공으로 기록하지 않는다.
`--tests`는 각 `Test` 태스크에 적용되므로 의도한 태스크 바로 뒤에 둔다.

## 기존 결과를 재사용할 조건

- 기준 커밋 이후의 차이와 미커밋 변경을 확인한다. 제품 소스뿐 아니라 관련 테스트·리소스·
  빌드·의존성·스키마·설정과 JDK·DB 등 실행 환경이 같아야 한다. 기준이나 환경이 불명확하면 해당 범위를 검증한다.
- 문서 수정·커밋 생성·동일 내용의 병합만으로 제품 검증은 무효가 되지 않는다.
  반대로 커밋이 같아도 로컬 변경이나 외부 환경이 달라졌다면 결과를 그대로 재사용하지 않는다.
- Gradle의 `UP-TO-DATE`·`FROM-CACHE`를 허용하고 결과에는 기존 결과 재사용이라고 적는다.
  매번 `clean`·`--rerun-tasks`·`--refresh-dependencies`를 붙이지 않는다. 캐시 문제를 조사할 때만 필요한 옵션을 쓴다.
- 범위가 좁은 마지막 수정은 해당 검증을 갱신한다. 다른 영역의 유효한 성공 근거까지 버리지 않는다.
  여러 선택 실행의 합계를 한 번의 전체 실행 결과처럼 보고하지 않는다.
- 검토에서 수정하지 않기로 한 항목은 필요할 때 이유와 재검토 조건을 짧게 남긴다.
  후속 검토는 관련 변경·새 실패·사용자가 추가한 범위부터 확인한다.

## 실패 후 조치

| 실패 원인 | 다음 실행 |
| --- | --- |
| 제품 동작 오류 | 원인을 수정하고 실패한 테스트, 영향받는 테스트 순으로 확인 |
| 문구·테스트 데이터·선택자 불일치 | 의도한 제품 동작과 테스트 기대값을 맞춘 뒤 해당 테스트 실행 |
| 런타임·의존성·권한·서비스 미기동 | 환경부터 수정하고 실패한 명령만 재실행. 조건을 바꾸지 않은 재시도는 하지 않음 |
| 일시적 실패 의심 | 로그·종료 상태를 남기고 같은 테스트로 재현 확인. 재실행 통과만으로 원인 해결을 선언하지 않음 |

표준 도구가 이미 제공하는 검증·캐시를 우선 사용한다. 보조 도구에 의존성이 없으면 기존 환경을 확인한 뒤
필요한 도구만 임시 환경에 준비한다. 같은 의존성이 없다고 확인한 런타임을 반복해서 시도하지 않는다.
범위가 넓은 실행과 실패 재현의 로그는 구분해 이전 실패 근거를 덮어쓰지 않는다.

## 다음 세션에 남길 근거

인수인계에는 현재 재사용할 결과만 남기고 오래된 실행 목록은 Git 이력으로 보관한다.
새 검증은 아래 항목을 필요한 만큼 한 행으로 기록하고 같은 범위의 이전 행을 교체한다.

| 기준 | 명령·범위 | 환경 | 결과·근거 | 남은 범위 |
| --- | --- | --- | --- | --- |
| 저장소·기준 커밋, 미커밋 변경 여부 | 실제 명령과 선택한 테스트 | 관련 JDK·DB·서비스 | 실행일, 통과/실패/재사용, 보고서·작업 기록 위치 | 제외·미실행·해결 안 된 실패 |

비밀과 원문 인증 정보를 기록하지 않는다. 임시 보고서를 삭제했다면 보존된 근거처럼 링크하지 않는다.
문서만 바꾼 작업은 링크·형식 검사 결과를 최종 응답·커밋에 남기면 충분하며, 제품 검증 행을 새로 만들지 않는다.
