# PRD-0010: 불변 에디션 리비전 근거

- 상태: 채택됨
- 결정일: 2026-08-20
- 범위: 에디션 항목의 집계 리비전·리비전 공백 근거 고정과 이전 스냅샷 호환성

## 목적

현재 `AttentionItem`은 적용한 `aggregateRevision`과 이전 리비전 사이의 공백 여부를
보존하지만, 에디션 항목은 이 두 근거를 고정하지 않는다. 따라서 사용자가 과거 에디션을
조회하면 당시 표시된 항목이 어떤 원본 리비전에 근거했고 공백 증거가 있었는지 알 수 없다.

새로 생성하는 불변 에디션 항목에 `aggregateRevision`과 `revisionGap`을 함께 고정한다.
두 값은 에디션 응답, 상태 지문과 에디션 비교에 같은 스냅샷 의미로 포함하며, 이미 생성된
에디션을 수정하거나 알 수 없는 과거 값을 추정하지 않는다.

## 에디션 항목 계약

PRD-0002의 에디션 항목에 다음 필드를 추가한다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `aggregateRevision` | 양의 정수 또는 `null` | 생성 시점에 선택한 관심 항목의 적용 집계 리비전 |
| `revisionGap` | 불리언 또는 `null` | 생성 시점까지 리비전 공백이 관측되었는지 여부 |

- 이 계약을 적용한 뒤 새로 저장하는 에디션 항목에는 두 필드를 모두 `null`이 아닌 값으로
  고정한다.
- 두 필드는 하나의 근거 쌍이다. 저장된 항목에서 둘 다 값이 있거나 둘 다 `null`이어야 하며,
  `aggregateRevision`이 있으면 양수여야 한다.
- 생성·전역 최신·주간 범위 최신·단건 조회와 PRD-0005 비교 응답은 저장된 값을 그대로
  반환한다. 현재 투영에서 값을 다시 읽거나 추정하지 않는다.
- `aggregateRevision` 또는 `revisionGap`만 달라도 에디션 항목의 의미가 다르다.

`AttentionItem` 투영 규칙과 에디션 선정 규칙의 의미는 바뀌지 않는다. 따라서 투영과
에디션의 `ruleVersion`은 계속 `1`을 사용하며 이 필드 추가만으로 새 규칙 버전을 만들지
않는다.

## 상태 지문과 생성 멱등성

- `stateFingerprint`는 기존 고정 항목 필드와 함께 `aggregateRevision`, `revisionGap`을
  정규 입력에 포함한다.
- 표시 필드가 같더라도 두 리비전 근거 중 하나가 달라지면 선택 상태가 바뀐 것이므로 새
  `generation`의 불변 에디션을 만든다.
- 이 계약을 적용해 처음 리비전 근거를 포함한 생성은 이전 지문과 달라 새 `generation`을
  만든다.
  이후 같은 요청 범위에서 같은 항목과 같은 리비전 근거를 다시 생성하면 가장 최근
  에디션을 멱등하게 반환한다.
- 새 지문을 도입해도 기존 에디션의 `stateFingerprint`, 항목, `generation`과 생성 시각을
  다시 계산하거나 덮어쓰지 않는다.

## 이전 에디션 호환성

Flyway V3 이전에 저장한 에디션 항목에는 정확한 `aggregateRevision`과 `revisionGap`이
고정되어 있지 않다.

- 이전 항목의 두 열은 `null`로 유지하고 조회·비교 응답에도 `null`을 반환한다.
- 수신 기록이나 현재 투영을 이용해 이전 값을 역산하거나 채우지 않는다.
- `0`과 `false`는 실제 값처럼 해석될 수 있으므로 미기록 값을 나타내는 기존 데이터
  채우기 값으로 사용하지 않는다.
- 이전 에디션과 새 에디션을 비교할 때 같은 비교 키의 근거 쌍이 `null`에서 실제 값으로
  바뀌면 PRD-0005의 `changed`로 반환한다.

이 호환성은 이전 스냅샷의 불변성과 알려지지 않은 사실을 정직하게 보존한다. 과거 항목의
근거가 `null`이라는 사실은 리비전이 없었거나 공백이 없었다는 뜻이 아니다.

## 영속성

- `brief_edition_item`에 `null`을 허용하는 `aggregate_revision`과 `revision_gap` 열을
  추가한다.
- 데이터베이스 제약은 두 열이 함께 `null`이거나 함께 값이 있어야 한다는 조건과 값이 있는
  `aggregate_revision`의 양수 조건을 소유한다.
- 애플리케이션의 신규 저장 경로는 두 값을 항상 함께 제공한다.
- 기존 행은 수정하지 않으며 별도 테이블, 인덱스와 이력 이벤트를 추가하지 않는다.

## 비교 계약

PRD-0005의 비교 키 `(reasonCode, sourceReference)`와 정렬은 그대로 유지한다.

- `added`와 `removed` 항목 및 `changed.before`·`changed.after`에 `null`을 허용하는 두 근거
  필드를 포함한다.
- 같은 비교 키에서 `aggregateRevision` 또는 `revisionGap`만 달라도 `changed`다.
- 비교는 각 에디션에 저장된 값만 읽으며 현재 투영이나 수신 기록을 조회하지 않는다.

## 수용 기준

- 새 에디션 항목이 양의 `aggregateRevision`과 `revisionGap`을 함께 고정하고 모든 에디션
  단건 응답이 저장된 값을 반환한다.
- Flyway V3 이전 항목은 두 값이 모두 `null`이며 `0` 또는 `false`로 기존 데이터를 채우지
  않는다.
- 두 열 중 하나만 `null`이거나 양수가 아닌 `aggregateRevision`을 저장할 수 없다.
- 표시 필드는 같고 리비전 근거만 달라진 첫 생성은 새 `generation`을 만들며, 이후 같은
  근거의 반복 생성은 그 에디션을 멱등하게 반환한다.
- 근거만 달라진 같은 키의 항목을 비교하면 `changed.before`·`changed.after`로 반환한다.
- 재구축이나 후속 수신 뒤에도 기존 에디션의 항목과 `null` 허용 근거가 바뀌지 않는다.
- 투영과 에디션 `ruleVersion`은 계속 `1`이다.

## 명시적 비목표

- 기존 에디션 항목의 리비전 근거 추정 또는 기존 데이터 채우기
- 새 HTTP 경로, 인증·인가와 외부 공개 API
- BATON 생산자 변경, 메시지 브로커와 스케줄러
- 에디션 선정·정렬 규칙 또는 `generation` 할당 변경
- 새 인덱스, 별도 변경 이력 테이블과 운영 배포
