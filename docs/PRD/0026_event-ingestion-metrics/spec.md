# PRD-0026: 이벤트 수신 결과 계측

- 상태: 채택됨
- 결정일: 2026-08-30
- 범위: HTTP 이벤트 수신 결과의 프로세스 내 집계

## 목적

`APPLIED`와 `APPLIED_WITH_GAP`은 모두 HTTP `202`, `DUPLICATE`와 `STALE`은 모두
HTTP `200`이다. HTTP 상태만으로 구분할 수 없는 이벤트 처리 결과를 집계한다. 기존 HTTP 지연·오류,
JVM과 연결풀 계측은 Spring Boot Actuator의 자동 구성을 사용하며 직접 복제하지 않는다.

## 계측 계약

- Micrometer `Counter` 이름은 `brief.events.received`다.
- 태그는 `outcome` 하나이며 기존 `IngestStatus` 여섯 값만 사용한다.
- 애플리케이션 기동 시 여섯 카운터를 `0`으로 등록해 첫 요청 전부터 수집할 수 있게 한다.
- 웹 어댑터가 수신 유스케이스의 결과를 정상 반환받은 뒤 요청당 한 번 증가시킨다.
- 이벤트 적용, 리비전 공백이 있는 적용, 중복, 오래된 리비전, 충돌과 미지원 결과를 각각 집계한다.
- 같은 이벤트의 재전달도 한 요청으로 센다. 따라서 저장된 수신 기록 수나 고유 이벤트 수가
  아니며, 최초 충돌 한 건의 보존 계약을 바꾸지 않는다.
- 인증·형식 검증 거부와 처리 도중 예외는 이벤트 결과 카운터에 넣지 않는다.
  이 실패는 기존 HTTP 상태·오류 지표로 확인한다.
- 직접 유스케이스 호출과 투영 재구축은 HTTP 이벤트 수신 요청이 아니므로 집계하지 않는다.
- 계측은 웹 어댑터에만 둔다. 도메인·application·영속성 모듈과 저장 스키마는 바꾸지 않는다.

## 보존·노출 경계

기본 실행은 PRD-0006에 따라 health만 제공한다. 지표 수집에는 ADR-0008의 선택적
`compose.observability.yml`을 사용한다. 이 구성은 컨테이너 내부 관리 서버에 지표를 제공하고
같은 서버의 Prometheus가 수집·경보 규칙을 실행한다. 외부 알림은 미연결이며 실제 설치와
검증 상태는 [운영 절차](../../operations/diagnostics-and-metrics.md)와 [HANDOFF](../../../HANDOFF.md)를 따른다.

카운터는 프로세스 메모리에 보관하며 재시작하면 초기화된다. 인스턴스별 합산과 증가율 계산은
수집 시스템이 담당한다. DB의 수신 기록을 읽어 카운터를 복구하지 않는다.

작업공간·시즌·이벤트 식별자, 원본 참조, fingerprint, 본문과 자격 증명을 태그에 넣지 않는다.
수신 시각이나 카운터만으로 BATON 이벤트의 전달 완료 여부나 장애 유무를 단정하지 않는다.

기본 실행과 Caddy 허용 경로는 바꾸지 않는다. 원격 수집기를 연결하려면 비공개 접근 경로·
인증·수집 주체를 별도로 정한다. 카운터 구현만으로 운영 모니터링이 완료됐다고 기록하지 않는다.

## 수용 기준

- 요청 전에도 여섯 결과의 카운터가 `0`으로 존재하고 첫 충돌·미지원 요청부터 증가한다.
- 기존 수신 통합 시나리오에서 여섯 결과별 실제 요청 수가 각각의 카운터 증가량과 일치한다.
- 기존 수신·충돌·리비전·재구축 결과와 HTTP 상태는 바뀌지 않는다.
- `/actuator/metrics`는 기본 실행에서 노출되지 않는다.
- Micrometer 표준 API와 기존 Actuator 자동 구성을 사용하며 별도 집계 저장소·래퍼·타이머를
  만들지 않는다.
