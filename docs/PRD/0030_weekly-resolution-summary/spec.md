# PRD-0030 주간 해소 요약

- 상태: 채택됨
- 목적: BATON에서 이번 주에 해소된 항목 수·목록·해소 시점을 현재 활성 항목과 구분해 보여준다.

## 조회 계약

`GET /api/v1/workspaces/{workspaceId}/seasons/{seasonId}/attention-items/resolutions`

### 요청

- `weekStart`·`zoneId`는 필수다. 기존 주간 브리프와 같은 월요일·IANA 시간대 검증을 사용한다.
- 조회 기간은 해당 시간대 월요일 자정부터 다음 월요일 자정 전까지이며 DST를 반영한다.
- `eventType`을 지정하면 해당 업무 종류의 해소 건수와 목록만 반환한다. 생략하면 전체 종류를 조회한다.
  기존 v1·v2 `SourceEventType`을 사용하며 변환할 수 없는 값은 `400 Bad Request`·`ProblemDetail`로 거부한다.
- `limit`은 기본 20, 범위는 1~100이다.
- `afterEventType`·`afterSourceReference`는 함께 제공하거나 생략한다.
  현재 목록과 같은 복합 식별자 오름차순으로 커서 다음 항목부터 조회한다.
  `eventType`은 필터이며 `afterEventType`은 커서다. 두 값이 달라도 커서 다음에서 조건에 맞는 항목을 찾는다.

예를 들어 역할 미배정 항목의 주간 해소는 다음 조건으로 조회한다.

```text
?weekStart=2026-08-24&zoneId=Asia/Seoul&eventType=ROLE_UNASSIGNED
```

### 응답과 다음 페이지

| 필드 | 의미 |
| --- | --- |
| `weekStart`, `zoneId` | 조회한 주차와 시간대 |
| `windowStart`, `windowEnd` | 조회 기간의 시작 시각(포함)과 끝 시각(제외) |
| `evaluatedAt` | 주입한 `Clock`의 조회 시각. 이 시각 이후에 발생한 해소는 제외 |
| `resolvedCount` | 해당 주차·업무 종류의 집계 조건을 만족하는 전체 항목 수. 커서와 페이지 크기에 무관 |
| `items` | 현재 페이지의 해소 항목 목록 |
| `nextCursor` | 다음 페이지 커서. 마지막 페이지는 `null` |

각 항목은 `reasonCode`, `sourceReference`, `resolvedAt`, `resolvedRevision`을 담는다.
해소 시각과 리비전은 집계에 사용한 활성→해소 전환의 값이며 이후 `RESOLVED` 갱신으로 바꾸지 않는다.
전체 건수와 현재 페이지는 한 SQL 문에서 같은 대상을 읽는다. 업무 종류 조건은 집계와 페이지 조회 전에
적용한다. 빈 페이지도 필터에 맞는 전체 건수를 반환한다. 일치하는 해소 항목이 없으면 `resolvedCount=0`,
빈 `items`, `nextCursor=null`을 반환한다.

페이지 조회 사이에 재활성화 등이 발생하면 목록과 건수가 달라질 수 있다. 최신 결과는 첫
페이지부터 다시 조회한다. BATON 화면은 다음 페이지의 주차·시간대가 이전 페이지와 다르면
목록을 감추고 첫 페이지 재조회를 안내한다.
필터를 사용하는 호출자는 다음 페이지에도 같은 업무 종류를 유지한다. 종류를 바꾸면 이전 커서를 버리고
첫 페이지부터 조회한다.

## 해소 집계

작업공간·시즌·이벤트 종류·원본 참조가 같은 최초 수신 기록 중 투영에 적용된
`APPLIED`·`APPLIED_WITH_GAP`만 사용한다. 다음 조건을 모두 만족하는 항목을 센다.

1. 마지막으로 적용된 `ACTIVE`의 바로 다음 원본 리비전이 `RESOLVED`다.
2. 현재 투영도 `RESOLVED`다.
3. 해당 해소 이벤트의 원본 발생 시각이 조회 기간 안이고 `evaluatedAt` 이하다.
4. 해소 이후 적용 기록에 새로운 리비전 공백이 없다.

연속된 `RESOLVED` 갱신은 해소 시점을 옮기지 않는다. 다시 활성화된 항목, 처음부터
`RESOLVED`인 항목, 활성과 해소 사이에 누락된 리비전이 있는 항목은 제외한다.
해소 이후 리비전 공백이 생기면 그 사이에 재활성화됐을 수 있어 제외한다.
이후 새로운 활성→해소 전환이 확인되면 그 전환을 기준으로 다시 판단한다.
중복·충돌·`STALE`·`UNSUPPORTED` 수신은 집계 근거로 사용하지 않는다.

이 수치는 해당 주에 해소된 뒤 현재도 해소 상태인 것으로 확인되는 항목 수다.
전체 업무 완료 수나 과거 특정 시점의 상태를 나타내지 않으며 재활성화나 새 수신 기록에 따라 줄 수 있다.
브리프 비교의 `removed`나 현재 항목의 마지막 `observedAt`으로 해소를 추정하지 않는다.
수신 기록과 현재 투영에서 조회하며 별도 저장 상태·규칙 버전을 추가하지 않는다.

## 서비스 경계와 호환성

- BATON은 사용자·작업공간·시즌 권한을 확인하고 시즌 시간대와 현재 주차를 정한다.
- 조회는 서비스 Bearer와 비공개 HTTPS 경로만 허용하며 공개 Caddy에는 추가하지 않는다.
- 기존 요청·요약 필드를 유지하고 같은 경로의 응답에 `items`·`nextCursor`를 추가한다.
  기존 이벤트·현재 목록·상태 변경 이력·브리프의 계약은 유지한다.
- BRIEF 응답과 서비스 Caddy 허용 경로를 먼저 배포한 뒤 BATON의 해소 요약 화면을 활성화한다.
- 구버전 BRIEF의 API 미지원과 `items` 필드 누락은 빈 조회 결과와 구분한다.
  해소 항목이 0건이거나 빈 목록인 것처럼 표시하지 않는다.
- 업무 종류 필터를 생략한 호출의 응답·정렬·커서는 유지한다. 필터용 테이블·인덱스·규칙 버전은 추가하지 않는다.
  BATON의 필터 중계·화면 연결은 별도 작업이며 BRIEF 조회 기능의 검증 범위에 포함하지 않는다.

## 검증 범위

- 실제 PostgreSQL에서 중복·오래된 전달·공백·재활성화·반복 해소에 따른 집계를 확인한다.
- 다른 작업공간·시즌의 항목 제외, 주간 경계와 고정 시각, 커서 전후의 전체 건수·빈 마지막 페이지를 확인한다.
- 업무 종류 필터의 v1·v2 결과, 필터 생략·빈 결과·잘못된 값, 필터와 커서의 독립성을 확인한다.
- 재활성화 뒤 재구축해도 같은 해소 시각·리비전을 반환하는지 확인한다.
- 서비스 인증과 비공개 HTTPS 허용 경로를 확인하고 공개 경로에서는 조회를 차단하는지 확인한다.
